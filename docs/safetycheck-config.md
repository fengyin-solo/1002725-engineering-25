# 安全巡检配置说明

安全巡检的**巡检要点**、**隐患等级与整改期限默认天数**、**示例巡检数据**全部以
JSON 配置文件维护，随版本库一起发布。换现场、改要点、调期限只改配置文件，
不需要改动任何业务代码。

## 1. 文件位置

```text
backend/config/
├── safetycheck.json        # 巡检要点（按区域分组）+ 隐患等级整改天数（业务配置）
└── safetycheck.seed.json   # 安全巡检示例数据（部署时按它初始化）
```

两个文件都纳入 Git 版本管理，并随 Docker 镜像一起打包（见
`backend/Dockerfile` 的 `COPY . .`）。配置目录可用环境变量
`SAFETY_CONFIG_DIR` 整体覆盖，便于在同一镜像里切换不同现场的配置。

## 2. `safetycheck.json` 结构

```json
{
  "schema_version": 1,
  "areas": [
    {
      "code": "BERTH",
      "name": "码头泊位",
      "checkpoints": [
        { "code": "BERTH-01", "name": "系缆桩、护舷完好无变形", "risk_level": "一般" }
      ]
    }
  ],
  "risk_levels": [
    { "code": "GENERAL", "name": "一般", "deadline_days": 15 }
  ]
}
```

- `areas[].checkpoints[]`：巡检要点，按所属巡检区域分组；
  `risk_level` 必须引用 `risk_levels` 中已经存在的等级名称。
- `risk_levels[].deadline_days`：该等级隐患整改期限的默认天数，
  整改期限 = 隐患发现日期 + 默认天数。
- `code` 只在配置内部使用，页面展示与数据记录使用中文名；`code` 与名称都不允许重复。

### 整改期限口径

| 隐患等级 | 默认天数 | 计算规则 |
| --- | --- | --- |
| 重大 | 3 | 发现日期 + 3 天 |
| 较大 | 7 | 发现日期 + 7 天 |
| 一般 | 15 | 发现日期 + 15 天 |

期限是**纯日期计算**（`app/inspection.py` 的 `compute_deadline`），不读取系统时钟，
因此同一份配置和示例数据在两个环境（开发/生产、不同机器、不同时区）跑出来的
整改期限与初始化记录完全相同。

## 3. `safetycheck.seed.json` 结构

顶层为 `{ "records": [ ... ] }`，每条记录的必填字段：

| 字段 | 说明 |
| --- | --- |
| 巡检编号 | 幂等键，全文件不允许重复 |
| 巡检区域 | 必须是配置中已存在的区域名称 |
| 巡检要点 | 必须是该区域下已配置的要点名称 |
| 巡检日期 / 巡检人员 / 巡检状态 | 状态取值：待巡检、巡检中、待整改、已闭合 |
| 隐患等级 | 有「发现隐患」时必填，必须是配置中已有的等级 |
| 发现日期 | 有「发现隐患」时必填，格式 YYYY-MM-DD |
| 整改期限 | 可留空：导入时按「发现日期 + 等级天数」自动补算；若已填写则必须与配置算得的日期一致 |

## 4. 启动校验：缺项直接报错并点名缺哪一个

后端启动（`import app.main`，即 `Store` 初始化）时依次执行：

1. 两个配置文件是否存在、是否为合法 JSON；
2. 业务配置自身是否完整：区域/要点/等级必填项、天数是否为正整数、编码是否重复、
   要点引用的隐患等级是否存在；
3. 示例数据与配置是否一致：必填字段、区域与要点引用、等级引用、状态取值、
   巡检编号是否重复、整改期限是否与配置算得的一致。

任一环节不通过都会抛 `InspectionConfigError`，**服务无法启动**，
错误消息会指出缺的是哪一项，例如：

```text
安全巡检配置校验失败（隐患等级第 2 项缺少必填项「deadline_days」；
巡检区域「码头泊位」的要点第 1 项缺少必填项「risk_level」）

安全巡检示例数据校验失败（示例数据「SAFE-0002」的整改期限 2026-12-31
与配置不一致：隐患等级「重大」默认 3 天，发现日期 2026-09-02，应为 2026-09-05）
```

校验通过后，示例数据才会写入内存仓库；前端可通过
`GET /api/safetycheck/config` 读取到与启动时完全一致的区域要点与等级天数。

## 5. 幂等导入：同一份配置重复导入只生效一次

- 启动时自动导入一次；
- 运维侧可随时手动重新导入：

  ```bash
  cd backend
  .venv/bin/python -m app.bootstrap
  # 也可指定现场配置目录：
  SAFETY_CONFIG_DIR=/etc/port/safety .venv/bin/python -m app.bootstrap
  ```

- 判重键是**巡检编号**。第二次导入同一份示例数据时新增条数为 0；
  已有的巡检记录（包括运行期新建的、已经做过状态流转的）**整行保留，绝不覆盖**。
  只有示例数据里编号尚不存在的记录才会追加。

导入输出示例：

```text
[安全巡检配置] 导入完成：区域 4 个、巡检要点 12 条、隐患等级 3 个；示例记录新增 0 条，
因已存在跳过 4 条（跳过：SAFE-0001、SAFE-0002、SAFE-0003、SAFE-0004）
[安全巡检配置] 同一份配置重复导入只生效一次，已有巡检记录未被覆盖。
```

## 6. 换现场的操作步骤

1. 修改 / 替换 `backend/config/safetycheck.json`（区域、要点、等级天数）；
2. 同步修改 `backend/config/safetycheck.seed.json`（区域/要点必须引用新配置，
   整改期限可留空让程序补算）；
3. 本地起一次服务或运行 `.venv/bin/python -m app.bootstrap`，
   缺项会在启动阶段直接报错并点名；
4. 提交两个配置文件到版本库并部署——业务代码、前端代码都不需要改动。

## 7. 验证

```bash
cd backend
.venv/bin/python -m unittest discover -s tests
```

测试覆盖：配置缺项点名、示例数据与要点一致性、期限确定性、
两次独立加载结论相同、重复导入不覆盖已有记录。
